SECTION 01The problem: one session, three tasks

A real session — 2055c1f8 — started as "check my open tickets", then drifted into an unrelated data investigation, then into a bug fix in another area. Three unrelated threads in one transcript.

When it came time to find it again, /resume was no help: its picker shows an auto-summary, and it can't full-text search what was said inside a session. The work was effectively buried.

⚠
The root cause isn't recovery — it's scope.

A session that tries to be three sessions is unfindable and its context gets muddy. The fix is one task per session, each tagged so it's findable later.

SECTION 02One slug, everywhere

Pick a short kebab slug per task — no-show-fallback, zif-trace. Use that one identifier in three places, so the task is recognizable no matter where you look.

Slug → three destinations
Hover a box to trace its link. The slug is the single thread tying the task together.
💡
Why it works

claude -n <slug> sets the prompt box, the /resume picker entry, and the terminal title at once. Add a matching branch/worktree and the slug spans your whole environment.

SECTION 04The memory ecosystem

Recovery is only the first layer. As work settles, it distills into progressively more durable, more searchable forms — and each recall tool reaches a different layer.

From volatile transcript to durable, searchable knowledge
The live transcript fades (90 days); this KB captures every session, generates topical observations, and surfaces relevant past work back into Claude's context automatically.
  • Live transcript — the full JSONL of a session. Reachable with cont, cresume, cfind. Expires after 90 days.
  • claude-session-kb — this system. Every prompt is captured to ~/.claude-kb/data.db via hooks. When each session ends, DeepSeek extracts 3–7 topical observations with domain-specific tags. Pre-emptive recall injects matching past sessions into every new prompt's context. Persistent. Self-contained.
  • Auto-memory — the curated MEMORY.md notes, loaded into every session automatically.

SECTION 05Your knowledge base — what it is

This page is the human window into a system that's mostly invisible. Five hooks wired into Claude Code's lifecycle write every session to ~/.claude-kb/data.db, capture every tool call Claude makes (Read / Edit / Bash / Grep / MCP), generate topical observations via DeepSeek from both prompts and tool-call batches, distill cross-session lessons, and inject relevant past work into the context of every new prompt you send. The KB you're about to open is the manual interface: a graph of how sessions, observations and topical tags connect, plus full-text and semantic search across everything.

Open your knowledge base →
ℹ
Local & live

A small FastAPI backend (python app.py) owns ~/.claude-kb/data.db. The capture hooks write to it as you work; a background worker thread inside the same process summarises tool-call batches every 60s; the recall hook reads from the embedded index and injects context before each prompt. Claude can also query it directly via four MCP tools (search_my_sessions, get_session, find_sessions_by_file, list_lessons). Nothing leaves your machine except optional DeepSeek calls for observation generation, lessons and labels — section 11.

The rest of this page is the full guide: how the KB is organised, how to search and filter, how to read the graph, and the workflows it's actually good for.

SECTION 06The two views: cards overview & drill-down

The KB only ever shows one of two things, and you flip between them by clicking.

Overview — session cards (default)

The default view. The main pane is a scrollable column of session cards: each card has a kebab-case topic title (stuck-charges, opera-cloud, bem-1password), a strip of project + wt: worktree (when the session was started inside <repo>/.claude/worktrees/<name>/) + observation count + 📁 N (distinct files touched via PostToolUse capture) + relative time, the LLM's 1–2 sentence summary (or the session's prompt as a fallback), and a one-click Copy resume button.

The toolbar has a recent / activity sort toggle that re-orders the cards in place — recent-first when you want to see what you just did, activity-first when you want the heaviest investigations at the top.

📄
Why cards, not a chart

Earlier iterations tried a force-graph map and a project-swimlane timeline. Both collapsed into noise at ~100 sessions: any 2D layout that labels every dot loses to text density. Cards put text where text belongs.

Drill-down — one session expanded into a force graph

Click any session card and the view switches to drill-down. The session becomes the teal anchor at the centre of a force graph. Its observations and summaries fan out as smaller coloured nodes (colours described in section 09). Each node is labelled with a 2-token kebab derived from the observation's topical tags (e.g. pms-zs-1837, booking-expedia) — never a generic English word like “Reservation”. A teal session banner across the top of the drill-down view always shows which session you're in (kebab label + project + worktree + observation count + summary). A records list of the same observations fills the middle pane; the detail panel on the right shows whichever item you click. The ← all sessions button (top of the graph pane) takes you back to the cards.

🔗
Search re-shapes the overview

Typing a query in cards mode swaps the cards from sessions to records (observations and summaries) — one card per hit, ranked by the API, with a clickable from session: <kebab> link that drills into the source session. The sort chips hide; relevance is the order.

SECTION 07Searching: keyword vs semantic

Two modes; one button. The chip in the toolbar toggles between them.

Keyword

Substring + token match across record title, subtitle, full text, facts, concepts, and file basenames. Server-side, ranked by where the match landed (title hits weighted higher). Instant. The default.

Use it when you remember a literal word from the data: an identifier (AWAITING_CHECKIN), a session id prefix, a file name, a hotel code, a person's name.

Semantic

Toggle the semantic chip. Your query is embedded server-side with the same all-MiniLM-L6-v2 model used to embed the records, then ranked by cosine similarity. No keyword overlap required — it finds matches by meaning.

Use it when you remember the shape of what happened but not the words. Examples that work:

  • "why do charges get stuck and never post" → the AWAITING_CHECKIN deferral investigation
  • "alerting when a hotel integration goes down" → the OXI outage monitoring sessions
  • "that thing about credit card fees" → the right session even if it never said "fees"
⏱
First semantic search is slow

On the very first run, the server has to embed every record once (~5–6 min on CPU). It's cached afterward, so every restart and every later search is instant. The toolbar shows indexing semantic… while it's building.

SECTION 09Reading the drill-down graph

The drill-down is the only graph in the app. Learning to read it makes the second half of every workflow faster.

Node colours

ColourMeans

Violet (#a78bfa)Summary or decision — structured rollups, decisions made

Node size roughly tracks importance — the session anchor is biggest; observation nodes are all the same small size.

Edges

  • Solid edge — "owns" link: the session owns its observation
  • Dashed edge — observation ↔ file connector (the file is touched by that observation)

Interactions

  • Click an observation node — the detail panel on the right fills with the full text, facts, files, concepts, and a copy-resume button. Neighbours stay visible; everything else dims.
  • Hover any node — same as click but temporary: neighbours highlight, label is revealed.
  • Click a file connector (slate node) — sets the file's basename as the search query and filters globally.
  • Click a result row in the records list — selects that observation in the graph too (graph and list stay in sync).
  • ← all sessions button (top of the graph pane) — returns to the cards overview.

SECTION 10Workflows — how you'll use it

These are the actual jobs the KB is good at. Each is one or two clicks.

"What was that session about?"

  1. Scan the cards — kebab title + 1–2 sentence summary is right there.
  2. Need more? Click the card to drill in; the observation list and detail panel fill out the rest.

"Find a past investigation by what was said in it"

  1. Switch to semantic.
  2. Describe it in plain language — the way you'd say it out loud.
  3. The top record cards land the right matches even with no keyword overlap; click from session: <kebab> to drill in.

"Recover a Claude Code conversation"

  1. Find the session (scroll the cards, sort by recent, or search).
  2. Copy resume is right on the card — one click, no drill needed.
  3. Paste in your terminal: claude --resume <uuid>. You're back in that conversation with full context.

"What sessions touched my file X?"

  1. Type the filename in the search box.
  2. Each record card shows the session it came from via the from session: <kebab> link.
  3. Or drill into any session that touched the file and click the slate file-connector node to filter globally.

"Show me only this project"

  1. Project dropdown → pick the project.
  2. The cards rebuild with just that project's sessions.

"Did I already solve this?"

  1. Semantic search a description of the problem.
  2. If it returns a record card: read the snippet, click from session to drill in for the summary + sibling observations. Usually faster than re-solving.

"What did I do recently?"

  1. Default cards view is already sorted by recent. Just scroll.
  2. Flip to activity if you want the heaviest sessions at the top instead.

SECTION 11Live freshness & LLM clarification

Live freshness (always on)

The browser keeps an EventSource open to /api/stream. Every few seconds the server checks if ~/.claude-kb/data.db grew (new prompts captured, new observations generated). When it does, the server reloads in place and pushes a refresh event — the page silently re-runs the current view and you see "↻ updated with new entries" flash in the status bar.

You never restart the server, never reload the page. The KB stays in sync with whatever Claude Code is doing.

LLM observations, lessons & labels (optional, opt-in)

If DEEPSEEK_API_KEY is set in the environment, five things happen automatically:

  • 3 to 7 topical observations per session on the Stop hook — each with a type (discovery, change, bugfix, decision, refactor, feature), a one-line title, 1–2 sentences of detail, and 2–5 domain-specific tags. The system prompt explicitly bans generic tokens like how-it-works / what-changed; a client-side filter drops anything that sneaks through.
  • 1 to 4 observations per tool-call batch from a background worker thread that runs inside the FastAPI process. It wakes every 60s, finds sessions with pending tool calls older than 5min, and hands each batch (up to 50 calls) to DeepSeek. Output shape is identical to the prompt-driven observations — same topical-tag rules, same anti-filler invariant — but titles are past-tense and name the concrete file or identifier touched.
  • Cross-session lessons when you run POST /api/lessons/distill?days=N: 5–15 durable patterns across the last N days of observations (project conventions, architectural decisions, recurring bug pedigrees) with kebab titles and source-session back-links. list_lessons MCP tool surfaces them to Claude.
  • A kebab-case topic label per session — 1–3 lowercase words joined by hyphens (stuck-charges, oxi-outage-probe, bem-stripe-cdp-fix), shown on every card.
  • A 1–2 sentence summary per session — shown directly on every session card and in the detail panel.

Cost is pennies on the first run; everything caches to .cache/llm.json keyed by sha256(model + kind + system_prompt + payload) — tweaking any system prompt invalidates only its own entries. New sessions get enriched incrementally as their Stop hook fires; tool-call batches drain incrementally as the worker ticks.

🔒
Privacy

Enabling DeepSeek sends session content (your prompts + observation titles + truncated tool inputs) to their API under their TOS. Sessions can contain confidential project data. To disable: unset DEEPSEEK_API_KEY — capture + recall keep working; tool-call queue accumulates without summarisation; observation/lesson generation falls back to a regex-based topical-tag extractor or is skipped.

SECTION 12Under the hood

One Python process, one HTML page, five hooks, four MCP tools, one inline background worker.

data flow
Capture hooks write sessions, prompts, and every tool call to ~/.claude-kb/data.db; a background worker thread in the same FastAPI process drains the tool-call queue into observations every 60s; the recall hook reads the embedded index and injects context. Web UI and MCP tools are both views over the same store.
  • app.py — FastAPI: REST endpoints + SSE channel + capture/observe endpoints + recall endpoint + lessons endpoints + the background tool-call summarizer thread. Serves the static frontend with no-cache headers and version-busted asset URLs.
  • store.py — in-memory view of ~/.claude-kb/data.db: sessions, observations, projects. Reloads when the DB grows. Exposes filesCount + worktree on each session.
  • store_capture.py — the capture store: sessions / prompts / observations / tool_calls / session_files / lessons tables with lightweight migrations; thread-safe writers.
  • observe.py — three DeepSeek system prompts: per-session observations from prompts, per-batch observations from tool calls, and cross-session lessons distillation. Client-side regex tag extractor for bulk imports.
  • embeddings.py — embeds observations with all-MiniLM-L6-v2; persistent cache in .cache/vectors.npy; runs cosine search server-side.
  • llm.py — DeepSeek client for kebab labels + summaries; lazy; hash-keyed cache in .cache/llm.json.
  • mcp_server.py — stdio MCP server exposing search_my_sessions, get_session, find_sessions_by_file, list_lessons as one-call tools for Claude.
  • hooks/recall.py — UserPromptSubmit hook: hits /api/recall (which ranks by cosine × time-decay + file-overlap-boost), formats the result as additionalContext.
  • hooks/capture.py — SessionStart / UserPromptSubmit / PostToolUse / Stop hook dispatcher: writes lifecycle, prompts, every tool call (with extracted files), triggers observation generation on completion.
  • static/kb.js — in-browser logic: card rendering (session + record), D3 force-graph drill-down, search debouncing, EventSource handling, detail panel, session banner.
